# IM 服务性能测试规范

## 1 总则

### 1.1 目的
规范 IM（即时通讯）服务的性能测试方法，统一测试场景、测试指标、数据采集方式和评判标准，确保测试结果可复现、可对比。

### 1.2 适用范围
适用于 IM 服务及同类 IM 服务的性能基准测试。

### 1.3 术语定义

| 术语 | 定义 |
|------|------|
| 发送阶段 | 从接收客户端请求，到消息落库，再到返回发送确认 |
| 分发阶段 | 读取分发目标列表，将消息时间线记录插入各目标并落库 |
| 通知阶段 | 检查目标用户 session，若在线则推送新消息通知 |
| 推送阶段 | 检查目标用户 session，若离线且满足推送条件则触发离线推送 |
| 拉取阶段 | 客户端收到通知或重连后请求离线消息，服务端读取并返回 |
| 发送速率 | 单位时间内成功发送的消息条数（条/秒） |
| 单核速率 | 发送速率 ÷ 服务端核心数 |
| 单核分发/广播速率 | 单核速率 × 群（聊天室）人数 |

## 2 测试环境规范

### 2.1 硬件环境

| 测试场景 | IM 服务器 | 数据库服务器 | 说明 |
|----------|-----------|-------------|------|
| 长连接测试 | 16C32G（腾讯云标准 S6） | 4C8G（腾讯云 MySQL） | 单机部署 |
| 单聊消息测试 | 8C32G（腾讯云标准 S6） | 8C16G（腾讯云 MySQL） | 合计 16C48G |
| 群聊消息测试 | 8C32G（腾讯云标准 S6） | 8C16G（腾讯云 MySQL） | 合计 16C48G |
| 聊天室消息测试 | 8C16G（腾讯云标准 S6） | 1C2G（可忽略） | 聊天室消息主要走内存 |
| 集群测试 | 4×4C8G（腾讯云标准 S6） | 8C16G（腾讯云 MySQL） | 1~4 节点逐级扩展 |

### 2.2 软件环境

| 组件 | 规格 |
|------|------|
| IM 服务 | IM 服务（单节点） |
| 数据库 | 腾讯云 MySQL |
| 压测客户端 | 模拟客户端（非真实设备），支持并发连接与消息收发 |
| 观察客户端 | 至少 1 台真实手机客户端，用于验证消息实时接收 |

### 2.3 网络环境
- 压测客户端与 IM 服务器处于同一云区域（建议同可用区），减少网络抖动干扰。
- 观察客户端使用公网接入，模拟真实用户网络条件。

## 3 测试用例

### 3.1 长连接测试（TC-LC-001）

#### 3.1.1 测试目标
验证单台 IM 服务在百万级并发长连接下持续在线的稳定性。

#### 3.1.2 测试参数

| 参数 | 值 |
|------|-----|
| 并发连接数 | 1,000,000 |
| 持续时间 | ≥ 30 分钟 |
| IM 服务器 | 1 台，16C32G |
| 数据库服务器 | 1 台，4C8G MySQL |

#### 3.1.3 操作步骤
1. 部署单节点 IM 服务并连接 MySQL。
2. 启动模拟客户端，逐步建立连接至 1,000,000 个并发连接。
3. 维持所有连接在线，不发送业务消息。
4. 持续观察 ≥ 30 分钟，记录连接状态与服务资源占用。
5. 逐步关闭连接，清理环境。

#### 3.1.4 判定标准

| 指标 | 合格标准 |
|------|----------|
| 掉线率 | 0%（30 分钟内无掉线） |
| IM 服务 CPU | 不超过 12 核（16C32G 环境下） |
| MySQL 利用率 | 接近 0% |

#### 3.1.5 参考基准

| 指标 | 实测值 |
|------|--------|
| 是否稳定 | 是，30 分钟以上无掉线 |
| IM 服务 CPU | ≈ 10 核 |
| MySQL 利用率 | 0% |

### 3.2 单聊消息测试

#### 3.2.1 发送消息测试（TC-SC-001）

##### 测试目标
仅测试消息发送阶段（接收方离线），排除通知和拉取开销。

##### 测试参数

| 参数 | 值 |
|------|-----|
| 发送用户数 | 200 |
| 接收用户数 | 1,000（999 离线，1 在线观察） |
| 发送轮次 | 50 轮 |
| 消息总量 | 10,000,000 条 |
| 服务资源 | 合计 16C48G |

##### 操作步骤
1. 创建 200 个发送用户和 1,000 个接收用户。
2. 1 个接收用户使用真实手机客户端保持在线。
3. 其余 999 个接收用户保持离线。
4. 200 个发送用户同时向 1,000 个接收用户各发送 1 条消息，完成 50 轮。
5. 记录发送时长、消息成功率、服务端资源占用。
6. 验证观察客户端接收消息的条数和实时性。

##### 判定标准

| 指标 | 合格标准 |
|------|----------|
| 消息成功率 | 100% |
| 消息完整性 | 观察客户端接收条数正确 |
| 发送延迟 | 肉眼无法察觉（发送结束后消息立即收齐） |
| 后置条件 | 发送结束后服务端压力迅速降为 0 |

##### 关键指标计算公式

```
发送速率（条/秒）        = 消息总量 ÷ 发送时间
单核速率（条/秒/核）     = 发送速率 ÷ 核心数
单核分发速率（条/秒/核） = 单核速率 × 2（单聊分发给发送者和接收者）
```

##### 参考基准

| 指标 | 值 |
|------|-----|
| 消息总量 | 1,000 万条 |
| 成功率 | 100% |
| 发送时间 | 509 秒 |
| 发送速率 | 19,646 条/秒 |
| 单核速率 | 1,227 条/秒/核 |
| 单核分发速率 | 2,455 条/秒/核 |

### 3.4 聊天室消息测试

#### 3.4.1 通用说明
- 聊天室消息主要走内存广播，数据库压力可忽略。
- 聊天室场景允许少量丢消息（设计使然）。
- CPU 峰值受网络瓶颈限制可能无法达到 100%。

#### 3.4.2 测试参数矩阵

| 消息总量 | 10,000 | 10,000 | 10,000 |
| 服务资源 | 8C16G | 8C16G | 8C16G |

#### 3.4.3 通用操作步骤
1. 指定数量的客户端加入聊天室。
2. 100 个发送客户端在聊天室内同时发送消息，每个客户端发送 100 条。

#### 3.4.4 通用判定标准

| 指标 | 合格标准 |
|------|----------|
| 消息落库成功率 | 100% |

| 指标 | 值 |

| 发送速率 | 21.5 条/秒 |

- 稳定后，单核广播与拉取速率收敛在约 13,000 条/秒/核。

### 3.5 集群性能测试

#### 3.5.1 测试目标
验证集群扩展能力，建立多节点场景下的性能估算模型。集群扩展并非线性（节点间 RPC 消耗额外资源），需实证确定扩容系数。

#### 3.5.2 集群架构说明
- 用户以**一致性哈希**分散到各节点，可视为均匀分布。
- 发送方和目标方不在同一节点时，消息需通过集群 RPC 转发。
- 节点数越多，RPC 消息占比越高：单节点 0% → 2 节点 50% → 3 节点 66.7% → 4 节点 75% → 趋近 100%。

#### 3.5.3 测试参数

| 参数 | 值 |
|------|-----|
| IM 服务器 | 4 台，每台 4C8G |
| DB 服务器 | 1 台，8C16G MySQL |
| 压测机 | 1 台，4C8G |
| JVM 堆内存 | -Xmx4G -Xms4G（每节点） |
| 测试场景 | 单聊发送消息 |
| 发送用户数 | 200 |
| 接收用户数 | 200（全部离线） |
| 发送轮次 | 20 |
| 消息总量 | 804,000 条 |
| 消息内容 | 12 汉字，约 36 字节 |

#### 3.5.4 操作步骤
1. 部署 4 台 IM 服务器，配置 Hazelcast 集群互发现（TCP-IP 模式，填写全部节点内网 IP）。
2. 修改 `im-server.conf`：为每个节点分配唯一 `node_id`（1~127），设置 `server.ip` 为当前节点内网 IP。
3. 启动单节点，执行压测 → 等待 3 分钟（服务 load 降至 0）。
4. 加入第 2 个节点 → 等待 3 分钟（缓存迁移）→ 执行压测（2 次，第 1 次热机，以第 2 次为准）。
5. 重复加入第 3、第 4 节点，每轮执行相同流程。
6. 验证集群状态：`curl http://授权地址/api/version`，确认 `nodeIds` 包含所有节点 ID。

#### 3.5.5 测试结果（参考基准）

| IM 节点数 | CPU 核心数 | 消息总量 | 发送时长 | 总体发送速率 | 单核发送速率 |
|-----------|-----------|----------|----------|-------------|-------------|
| 1 | 4 | 804,000 | 123 秒 | 6,537 条/秒 | 1,634 条/秒 |
| 2 | 8 | 804,000 | 85 秒 | 9,459 条/秒 | 1,182 条/秒 |
| 3 | 12 | 804,000 | 60 秒 | 13,400 条/秒 | 1,117 条/秒 |
| 4 | 16 | 804,000 | 50 秒 | 16,080 条/秒 | 1,005 条/秒 |

#### 3.5.6 集群性能模型

**RPC 与本地处理推导**（基于 4C8G 节点）：

```
本地消息单核速率 = 1,634 条/秒/核（单节点，无 RPC）
RPC 消息单核速率  ≈ 800 条/秒/核（推导值，约为本地的 50%）

推导过程（以 2 节点为例）：
  单核速率 1,182 = 本地 50% + RPC 50%
  本地贡献 = 1,634 × 0.5 = 817
  RPC 贡献 = 1,634 × 0.5 × x  →  x = (1182-817)/817 ≈ 0.45
  RPC 单核速率 ≈ 1,634 × 0.5 ≈ 800 条/秒

3 节点验证：1,634 × 0.333 + 800 × 0.667 = 1,078 ≈ 实测 1,117
4 节点验证：1,634 × 0.25 + 800 × 0.75 = 1,009 ≈ 实测 1,005
```

**系统整体扩展规律**：

```
每增加 1 个节点，系统整体吞吐增加约单节点能力的 50%：
  1 节点：6,537 条/秒  （基准）
  2 节点：9,459 ≈ 6,537 × 1.5
  3 节点：13,400 ≈ 6,537 × 2.0
  4 节点：16,080 ≈ 6,537 × 2.5
  N 节点：≈ 6,537 × (1 + (N-1) × 0.5)
```

**带数据库开销的修正**（IM 与 DB 资源比约 2:1）：

```
本地单核速率（含 DB）= 1,634 ÷ 1.5 ≈ 1,089 条/秒/核
RPC 单核速率（含 DB） = 800 ÷ 1.5 ≈ 533 条/秒/核
```

#### 3.5.7 集群容量估算公式

```
N 节点集群吞吐量 ≈ 单节点吞吐量 × (1 + (N-1) × 0.5)
                 ≈ 单核本地速率 × 单节点核心数 × (1 + (N-1) × 0.5)

示例（4C8G 节点，单核 1,089 条/秒 含 DB，4 节点）：
  吞吐量 ≈ 1,089 × 4 × (1 + 3 × 0.5) = 1,089 × 4 × 2.5 = 10,890 条/秒
```

#### 3.5.8 集群测试注意事项
- 每轮测试执行 2 次，**第 1 次热机**，以第 2 次数据为准。
- 节点加入后等待 ≥ 3 分钟，完成缓存迁移。
- 每次测试后等待 IM 服务 load 降至接近 0 再开始下一轮。
- DB 资源配置为 IM 总资源的 50%，避免 DB 成为瓶颈。
- 高并发压测可能导致内存不足，需适当调整 Hazelcast 缓存比例或重启节点。

### 3.7 推送服务测试

#### 3.7.1 架构说明

推送服务是独立于 IM 服务的子系统，工作流程为：

```
客户端注册推送 → 获取 deviceToken → setDeviceToken(token, type) → IM 服务存储
    ↓
用户离线 + 有新消息 → IM 服务推送决策 → 符合条件 → 打包推送数据 → HTTP 调用推送服务
    ↓
推送服务 → 根据 type 选择厂商（华为/小米/OPPO/Vivo/魅族/APNs/FCM）→ 调用厂商 SDK 推送
    ↓
厂商通道 → 通知栏消息 或 透传激活应用 → 应用连接 IM 收消息 → 本地通知
```

#### 3.7.2 推送服务端口

| 端口 | 用途 | 访问路径 |
|------|------|----------|
| 8085 | 推送服务端口（IM 服务调用） | `/android/push`、`/ios/push`、`/harmony/push` |
| 8086 | Admin 管理端口 | `/api/admin/*`、`/admin/*` |

#### 3.7.3 推送决策条件（IM 服务端判断）

| 序号 | 条件 | 说明 |
|------|------|------|
| 1 | 客户端在线 | 在线则不推送 |
| 2 | 离线超过 7 天 | 可配置，超时不推送 |
| 3 | 消息无 pushContent | 内置消息默认处理，自定义消息需传入 |
| 4 | deviceToken 不存在 | 未注册推送则不推送 |
| 5 | 平台不支持推送 | 检查平台类型 |
| 6 | 会话被静音 | 静音且非 @消息时不推送 |
| 7 | PC 在线时静音 | PC 在线且设置静音时不推送 |
| 8 | 全局静音 | 全局静音时不推送 |
| 9 | 免打扰时段 | 在免打扰时间段内不推送 |

## 5 性能估算方法

### 5.1 消息处理阶段与性能模型

```text
发送阶段  ________ 单核 ≈ 1,227 条/秒/核  （单聊发送测试）
通知阶段  ├─ 单核 ≈ 2,978 条/秒/核  （单聊收发 - 发送 推导）
拉取阶段  ┘
分发阶段  ________ 单核 ≈ 8,750 条/秒/核  （千人群分发速率）
推送阶段  ________ 低开销（仅 HTTP 调用推送服务）

单聊分发速率 ≈ 8,750 条/秒/核（与群聊分发一致，分发给 2 个目标）
单聊开销 ≈ 1÷1227 + 1÷8750 ≈ 1÷1077，即单聊整体约 1,077 条/秒/核
群聊开销 ≈ 1÷1227 + 1÷8750 （1 条消息 ≤ 1,000 目标时）
聊天室广播 ≈ 13,000 条/秒/核（内存广播，不经 DB 分发）
```

### 5.2 容量估算公式

**单机场景：**

```
单聊消息：所需核心数 = 预估消息量(条/秒) ÷ 1,077 × 安全系数(≥1.5)
群聊消息：所需核心数 = 预估消息量(条/秒) ÷ 发送单核速率 × 安全系数(≥1.5)
聊天室：  所需核心数 = 预估消息量(条/秒) ÷ 广播单核速率 × 安全系数(≥1.5)
长连接：  所需核心数 = 预估连接数 ÷ 100,000（16C 支撑约百万连接）
```

**集群场景（单聊消息，4C8G 节点）：**

```
N 节点集群吞吐量 ≈ 单节点吞吐量 × (1 + (N-1) × 0.5)
                 （每增加 1 节点，增加约 50% 单节点能力）
IM 与 DB 资源配比 ≈ 2:1
DB 配置建议 ≥ IM 总核心数 ÷ 2
```

### 5.3 集群 vs 单机性能对比

| 指标 | 单机（8C32G） | 4 节点集群（4×4C8G） | 说明 |
|------|--------------|---------------------|------|
| 总核心数 | 16C（含 DB） | 16C IM + 8C DB | 集群多了 DB 核 |
| 本地单核速率 | 1,227 条/秒 | 1,634 条/秒 | 相同 IM 版本，不同资源配比 |
| 实际吞吐量 | 19,646 条/秒 | 16,080 条/秒 | 集群 RPC 损耗约 18% |
| 扩展性 | 不可扩展 | N 节点可扩展 | 集群支持动态扩容 |

### 5.3 影响因素

| 因素 | 影响 |
|------|------|
| 消息体大小 | 消息越大，性能越低；大消息场景需单独压测 |
| 媒体类消息 | IM 服务仅处理 2 次交互（获取上传 token + 发送消息），压力主要在对象存储 |
| 缓存命中率 | 离线消息若在缓存，性能优于冷数据（需读 DB） |
| 离线消息比例 | 离线消息多 → 拉取阶段占比高 → 需评估缓存命中率的影响 |
| 用户信息/群组信息强制刷新 | 单次拉取消耗极低，但滥用会导致超频限流。应在关键界面仅刷新 1 次 |
